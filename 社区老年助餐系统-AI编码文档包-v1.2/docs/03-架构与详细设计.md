# 03 架构与详细设计

> 开发技术版本和操作系统以 `11-Ubuntu环境与版本锁定.md` 为准。

## 1. 最小可用技术架构

浏览器 Vue3 SPA → HTTPS REST → Spring Boot 单体业务服务 → MySQL8；前端 ECharts 展示报表。Spring Boot 内部 `forecast` 和 `recommendation` 纯 Java 计算模块，**不用 Python/机器学习服务**。模拟支付网关为业务模块接口实现，真实支付集成可替换。

## 2. 后端工程组织（建议）

```
server/src/main/java/com/community/meal/
  common/            // ApiResponse、分页、统一异常、校验、时钟、文件上传
  auth/              // 登录、Spring Security、角色与网点资源权限
  user/              // 用户、角色、网点员工绑定
  site/              // 网点、停餐日期
  elder/             // 老人档案、家庭绑定、健康资料
  subsidy/           // 资格申请、审核、权益
  dish/              // 标准菜品、食材/过敏原、营养、价格
  menu/              // 日菜谱、报备、审核、当日上下架
  order/             // 下单、周期代订、明细、状态与凭证
  payment/           // 支付渠道接口、模拟、支付流水、回调
  refund/            // 取消申请、退款审批与执行
  redemption/        // 堂食/外带核销、配送状态
  forecast/          // 星期历史均值计算、快照、展示
  preparation/       // 备餐清单与人工调整
  recommendation/    // 规则过滤、可解释评分、参数
  nutrition/         // 膳食周期报告
  review/            // 菜品评价
  ticket/            // 投诉工单
  notice/            // 公告接收范围
  dashboard/         // 统计聚合
  audit/             // 关键操作审计
```

每业务模块至少 Controller → Service → Mapper → Entity/DTO/VO；Service 包含事务边界。Controller 仅校验与调用，Mapper 不允许绕过 `site_id`/关联人权限过滤。

## 3. 前端工程组织（建议）

```
web/src/

       recommendation,preparation,nutrition,review,ticket,notice,dashboard,audit}.ts
  router/index.ts
  stores/{auth,site}.ts
  layouts/{AdminLayout,StaffLayout,FamilyLayout}.vue
  views/admin/*
  views/canteen/*
  views/family/*
  views/community/*
  components/{DishCard,MoneyDisplay,OrderStatus,MealChart,Upload}.vue

```

页面只显示角色允许的菜单，访问路由时做前端守卫；**后端永远独立重复鉴权**。家属端提供响应式布局和可调大字号。

## 4. 接口层规范

- JSON UTF-8，所有资源 `/api/v1/...`；Token 认证，Bearer Header；明细 GET、搜索 GET、写入 POST/PUT/PATCH，删除尽可能软删除。
- 通用响应 `{"code":"OK","message":"success","data":{},"traceId":"..."}`；业务错误 `code` 稳定枚举；列表分页使用 `page=1,size=20`，`data={"records":[],"total":0}`。
- 金额传 decimal 字符串如 `"12.50"`；日期为 `YYYY-MM-DD`，时间 ISO 8601 带时区；枚举大写下划线。
- 同一 HTTP 请求的订单提交/付款通知/退款/核销均需 idempotency key 或数据库唯一约束；数据库事务隔离必须能防止重复预订与超售。

## 5. 权限实现

- 用户与角色 N:N（一个人原则上可多个角色）；管理员全局；工作人员/社区操作员只能访问 `user_site` 表授予网点；家属仅可访问 `elder_family_binding.status=APPROVED` 关联老人及本人订单/支付/反馈。
- 操作员创建老人档案需选择授权网点；审批时只处理本网点老人；网点变更涉及关联记录权限同步。
- 老人健康信息、证件材料、配送禁忌视为敏感：使用专用 DTO 返回最小字段；文件下载先校验资源拥有权和操作权限；日志不写敏感原文。

## 6. 关键一致性事务

- 下单：校验菜单发布、规则过滤、份数容量、同老人同日同餐次唯一活跃订单；写订单及快照、占位量、随机凭证种子。待支付超时释放占位；成功支付锁订单并转换确认量。
- 支付：支付单号唯一；回调先验签再按支付单唯一键幂等更新。模拟支付接口只能在 `dev/test` 配置运行。
- 取消/退款：审批、调用渠道、回写状态、回滚补贴统计、释放可售份数必须幂等。真实资金调用是外部边界：持久化退款状态，失败可重试，不可依赖单一数据库事务实现分布式原子性。
- 核销：事务内条件更新订单 `READY→COMPLETED` 且插入带 `UNIQUE(order_id)` 的核销记录；失败明确返回已核销/状态不合法。
- 统计：只汇总真实业务交易状态；软删除历史不能破坏追溯。

## 7. 预测和推荐详细模块

### 预测

- `ForecastService.predict(siteId, mealType, startDate, days<=7)` 读取历史营业日期，按 `02` 中相同星期均值/最近营业日回退规则算出结果。将预测快照记录到 `forecast_result`，同一天多次可有不同 `generated_at` 以便比较。
- 没有历史数据不能返回伪造预测；员工查询只限本网点。

### 推荐

- `RecommendationService.listForElder(elderId, siteId, date, mealType)` 先检验授权，再读取发布菜单、老人疾病/过敏原与菜品营养；硬规则过滤，未登记关键安全信息按 `02` 处理；对候选菜品评分并返回 `reasons`、`score`、`warning`。
- 不另建“推荐模型训练”，可直接实现 Java Service 的规则与算术。
- 下单端不信任前端推荐结果，服务器重新检查禁忌规则。

### 膳食报告

- `NutritionReportService.get(elderId, period)` 查已核销/已送达订单快照，以菜品实际份数加权汇总；不给医学结论。

## 8. 文件上传和可见性

存储本地开发目录 `./uploads/private`（生产可替换对象存储，但非首版要求）；数据库保存相对路径及拥有者。公开菜品图可单独只读映射；申请证明、评价图片和工单附件需业务鉴权、限制上传大小（建议单文件 5MB）与 MIME。禁止路径穿越。

## 9. 日志与报表

操作日志 `audit_log` 异常捕获、审批成功/拒绝、权限变更、价格调整、核销、退款；仪表盘聚合用 SQL 查询，数据量小不需数据仓库或缓存；按日期/网点/餐次筛选，给出统计口径说明。

## 10. 开发阶段验收建议

每阶段完成 DB schema + Entity + Mapper + Service + Controller + 前端页面 + 权限 + 自动测试。AI 不得先把所有前端页面做成纯 mock 再声称功能完成；必须连通真实后端。最终按 `10` 逐一验收。
