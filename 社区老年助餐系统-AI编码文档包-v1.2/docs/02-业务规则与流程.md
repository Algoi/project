# 02 业务规则、状态机与算法详细规则

> 以下“默认约定”用于保证首版可直接开发；除原需求明确写明的规则外，均可在上线前调整，不额外扩大功能范围。

## 1. 基础对象与数据边界

- 一个网点有多位工作人员/操作员，可由管理员授权；每名用户可关联多个网点，当前选择网点后操作。
- 老人归属一个主要服务网点；家属绑定老人经社区操作员核验通过才可查看健康档案与下单。可允许多位已审核家属绑定一位老人。
- 菜品是全局标准信息；网点每日菜谱引用菜品并设置当日可售数量及状态。菜品营养信息以标准“每份”为口径，订餐时保存价格和营养快照，避免后期修改影响旧订单与报告。
- 只支持午餐、晚餐两个餐次（默认午餐）。可在站点设置餐次可售，无早餐不影响原需求。

## 2. 价格与补贴

- 菜品字段 `original_price` 社会原价、`elder_price` 老人补贴价。**默认约定**：通过补贴资格的老人结算按 elder_price，未通过资格暂不享受补贴，按 original_price 结算；补贴金额 = 原价合计 - 实付前优惠合计（不小于 0）。
- 对所有条目分别计算再相加；价格和补贴金额生成订单快照。无额外满减/优惠券/额度阶梯。
- 支付金额 `payable_amount = original_amount - subsidy_amount`；金额不能为负。已审核补贴资格以订单创建时快照计算；资格之后撤销不追溯已完成订单。
- 支付渠道：`MOCK_A`, `MOCK_B` 用于开发模拟“多渠道”；上线真实渠道必须独立完成支付接入和结算验证，不能把模拟记为真实收款。
- **边界**：退款已支付金额按原支付渠道返回；补贴“发放统计”以成功/有效订单中享受补贴的金额汇总，退款成功作负向冲减。无真实政府补贴资金拨付子系统。

## 3. 订餐规则

- 菜谱必须 `PUBLISHED` 且菜品 `AVAILABLE`、网点有效、供餐日期未停餐，方可加入订单。
- 默认允许次日至未来 7 天预订；当天订餐截止为该餐次开餐前 2 小时（基于网点本地时区 `Asia/Shanghai`，部署时可配置），可配置；家属代订、社区代订一致。
- 同一老人/日期/餐次最多一笔未取消有效订单（创建时数据库约束或行级事务检查，避免并发）；一个订单多个菜品、每项大于 0 份；周期预订按天逐个创建订单，失败日期明确返回并可部分成功。
- 取餐方式：`DINE_IN`、`TAKEOUT`、`DELIVERY`；配送订单必填地址及联系人，无配送员独立账号。
- 预约份数不能超过当日菜谱 `planned_qty`（默认需要人工填写，允许 0 表示停售，严禁将 0 解释成无限）。成功支付计入已确认订单量，待支付数量暂占位 15 分钟后释放。
- 订单提交前再次执行服务端过敏原、疾病硬规则校验。健康资料缺失或过敏数据不完整时显示“资料不足，需人工确认”，不得声明菜品安全；对于已知高风险但无法判定的菜品不允许自动推荐，是否允许继续订购作为上线确认项，首版默认阻止。

## 4. 订单、出餐与核销状态

状态：`PENDING_PAYMENT` → `PAID` → `PREPARING` → `READY` → `COMPLETED`；
取消：`PENDING_PAYMENT` → `CANCELLED`；`PAID` → `CANCEL_REQUESTED` → `REFUND_PENDING` → `REFUNDED` 或 `PAID`（驳回）；
异常：保留独立 `exception_note`、`exception_flag`，不制造复杂的状态分支。

- `PAID` 但尚未进入 `PREPARING` 才能由家属申请取消；退款由操作员审核。`PREPARING` 与以后状态用户不可自行取消。未支付订单可直接取消。
- 食堂工作人员可将 `PAID`→`PREPARING`→`READY`（按网点）并打印清单；社区操作员可处理异常、取消申请，但不能随意强制确认支付。
- 取餐凭证为随机不可枚举一次性码（保存哈希，展示原始码仅在支付后获取凭证时）；仅 `READY` 状态可核销；核销后 `COMPLETED`，并写 `redemption` 唯一订单记录。
- 同一订单仅单次核销（订单多份餐视为同一次整单取餐），不做按份拆核销。
- `DELIVERY` 的交付完成不等同现场核销；首版配送清单和配送状态 `PENDING/OUT_FOR_DELIVERY/DELIVERED`，送达确认可以使订单完成；配送订单不得用堂食核销接口。

## 5. 退款规则

- `CANCEL_REQUESTED` 经有权社区操作员批准，写退款单 `APPROVED` 并调用支付网关，成功后 `REFUNDED`，支付流水记账；失败保持 `REFUND_FAILED` 可由操作员重试（幂等请求号）。驳回则恢复 `PAID` 并附原因。
- 仅整单退款（首版不做部分退款），每订单最多一笔成功退款；同一审批/回调不能重复资金及补贴冲减。

## 6. 菜谱与备餐规则

- 食堂提前录入次日菜单，状态 `DRAFT`→`SUBMITTED`；社区操作员确认当日可售 `PUBLISHED`；可临时将单个菜品置为 `OFF_SHELF`，已经支付的订单保留并提示人工处理，不自动退款。
- 报备时允许覆盖菜品标准克重/营养信息为“当日份量数据”，供该日订单快照使用；修改后新订单用新值，旧订单快照不变。
- 备餐清单包含：每菜品已支付且未退款订单件数 `confirmed_qty`；预测日就餐人数 `forecast_count`；备餐参考值 `suggested_qty`。
- **默认简单规则**：预测人数按历史各菜品订单比例分配为菜品建议份数；没有可靠比例则每菜品建议值=已确认份数，避免凭空增加具体菜品预测。`suggested_qty = max(confirmed_qty, round(forecast_count * historical_item_share))`，当历史份数的份额定义为**份数占历史总菜品份数之比**，考虑每位老人可买多项，因此分配总数量前需要历史平均每人份数校正：`forecast_total_items = round(forecast_count * avg_items_per_diner)`，再乘以 share。若历史少于 7 个有效营业日，则只展示预测人数、菜品建议=已确认数量。工作人员可人工修订备餐计划。

## 7. 时间序列人数预测（无机器学习）

目的：按网点按餐次预测未来 1~7 天人数，使用**实际完成/核销人数**作为历史值（配送使用成功送达），每日每位老人一次就餐计 1 人；不统计已取消及只支付未领取的订单。停餐日不作为 0 参与均值，应标注不营业。

输入：网点、餐次、目标日期、过去最多 56 个自然日中营业日的实际就餐人数序列；排除停餐和空缺数据，真实营业但 0 人的日期要保留 0。

步骤：
1. 选择目标日期相同星期的历史营业日期，优先取最近 8 次（最多 8 次）。
2. 若同星期样本数 >= 3：预测值为这几次人数算术平均，四舍五入至非负整数。
3. 否则若最近 14 个营业日有效样本 >= 3：取这 14 个营业日算术平均。
4. 否则返回 `insufficient_data=true`、预测值 `null`；前端显示“历史数据不足”，不返回伪造 0。
5. 目标为停餐日期：`closed=true`、预测值 `0`、注明“不营业”；不参与平均。
6. 每次调用可即时算出并保存预测快照供对比，包含 `algorithm=weekday_average_v1`、生成时间、样本数、所用日期、最终值。

展示：按未来 7 天列表/折线展示；管理员跨网点，食堂工作人员仅本网点；对历史相应预测快照与实际人数可做 MAE 简单比较，不必建立训练评估系统。

## 8. 智能膳食推荐（规则 + 可解释评分）

**先过滤、后评分**。可售菜单中，只要配料过敏原命中老人登记过敏原或匹配生效疾病“禁止”规则，就过滤。后台可配置疾病↔食材/菜品的禁止规则、过敏原名称和权重。不得按疾病名称自行假定医学禁忌清单；上线使用的具体规则需专业确认。

当日菜品计算四项 0~100 分（缺值按 50 中性分，过敏信息缺失按安全规则拦截）：
- `N` 营养适配：按后台配置的目标营养区间计分；无目标区间则 50，不得称为医疗推荐。
- `P` 偏好：匹配老人偏好的菜品类别为 100，不匹配为 50，明确不喜欢为 0。
- `R` 评价：菜品平均评分（1~5 星）线性转换 0~100，无评价为 50。
- `H` 历史：老人过去 30 天选择过同一菜品为 100、同一分类为 70，否则 50。

`score = wN*N + wP*P + wR*R + wH*H`，权重 >=0 且总和=1，默认 `0.4/0.25/0.2/0.15`；分数保留 2 位。并列按菜品名称/ID 稳定排序。展示过滤说明（不向用户公开其他人的健康信息）、推荐理由（如“符合偏好分类/评分较高”）。无足够健康数据时给出“信息不完整”提示。

推荐统计：记录推荐曝光 `recommendation_event`，以及订单明细可选 `recommendation_event_id` 关联，转化率 = 下单事件数 / 有效曝光事件数（同口径去重），管理员面板注明统计口径。

## 9. 膳食周期报告

按周/月查询核销完成/送达订单的**订单营养快照×实际份数**求和：热量 kcal、蛋白质/脂肪/碳水 g、钠 mg；按天分组显示趋势。报告声明“为本平台记录食物的估算营养摄入，未计算其他饮食、剩餐等”，不可称整体健康诊断。若无数据，返回空数据与说明。

## 10. 反馈/公告/审计

工单 `OPEN`→`IN_PROGRESS`→`RESOLVED`；重大事项 `ESCALATED`，允许管理员查看并回复；超时定义默认 48 小时未首次回复，前端显著标注但不自动处罚。公告 `DRAFT/PUBLISHED/REVOKED`，按角色、网点筛选；停餐公告仅通知，不会自动改变营业状态，管理员需在网点日历另行设置。重要审计包括人、时、资源、行为、结果、脱敏摘要。

## 11. 闭环示例

管理员创建网点和标准菜品 → 操作员建老人档案并审核补贴及家属绑定 → 食堂上报次日菜谱 → 操作员发布菜谱 → 家属选择老人并查看安全过滤后的推荐 → 下单及模拟支付 → 食堂查看预测并备餐、出餐 → 食堂/操作员核销 → 家属评价/提交投诉 → 操作员处理 → 家属和操作员查看膳食报告 → 管理员查看统计、预测和审计。

## 12. 上线前必须核对的少量决策

实际补贴政策及价格公式、适用餐次与订餐截止时间、绑定证明方式、真实支付渠道、疾病规则医学审核、文件留存期限、服务区域数据权限。这些不阻碍原型开发，但不可把默认规则直接认定为实际政策。
