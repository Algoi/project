## 2. 技术与实施边界

- Web 前端 Vue 3 + Vite + Element Plus + Axios + Pinia + ECharts；同一套 Web 项目按角色呈现页面，家属端支持移动浏览器适配和大字样式。
- 后端 Java 17 + Spring Boot 3 + Spring Security + MyBatis-Plus + MySQL 8；支付通过 `PaymentGateway` 接口封装，可本地模拟，不默认接入真实资金渠道。
- 预测：仅采用 **按网点、按星期历史均值 + 最近数据回退** 的时间序列统计预测；不引入 Python、机器学习、深度学习、训练平台。
- 膳食推荐：基于过敏原/疾病禁忌规则过滤，再按明确可解释的营养、偏好、评价权重评分；不是机器学习推荐系统。
- 膳食报告：依据系统已核销餐品的营养数据估算，不推断实际全部摄入、不提供诊疗结论。
- 部署：单体 Spring Boot + 单体 Vue + MySQL；不建设微服务、消息队列、数据仓库、Redis、移动原生 App。
- 原始的“多种支付渠道”保留支付渠道抽象与多渠道配置能力，联调可用模拟渠道，真实通道必须另行提供商户资质、密钥和回调文档。

## 3. 决策原则

**已确认**：用户给出的 33 项功能全部要求实现。

**实现默认约定（可替换，不等于原用户已确认）**：例如一位老人允许多家属绑定、补贴折算规则、每日订单截止、退款时限、餐次、价格快照；详见 02 文档。AI 编码不能把默认约定拓展为复杂产品。

**明确不做**：训练平台、LSTM、Prophet、复杂健康诊断、智能营养处方、配送路径优化、积分会员、库存采购入出库管理、财务总账、审批流引擎、地图围栏、短信网关、复杂组织层级、独立配送员角色。

## 4. 交付完成定义（DoD）

1. 33 项原始功能在 10-需求追踪矩阵中全部落实到页面/API/数据/测试。
2. `04-数据库设计.sql` 能在空 MySQL 8 数据库执行；种子数据包含四类角色、两网点、若干菜品、模拟订单及历史就餐数据。
3. 四角色使用不同测试账号可登录，跨角色与跨网点请求被后端拒绝。
4. 老人建档→补贴申请审批→菜品上报/上架→家属或操作员订餐→支付→备餐→核销→评价→膳食报告形成闭环。
5. 预测能显示未来多日数值、历史与预测曲线、备餐参考；过滤能给出禁忌原因，推荐能复现评分。
6. 所有资金、退款、核销、资格审核以及健康信息操作有后端权限校验、事务和审计。

## 5. 交给 AI 的总指令（可复制）

> 请严格以本目录文档为唯一产品需求依据，按 `08-AI编码任务清单.md` 顺序实现。不得遗漏 `10-需求追踪矩阵.md` 的任何功能，不得自作主张扩展 ML、微服务、库存、医疗诊断等模块。遇到未定规则，采用 `02-业务规则与流程.md` 的默认约定，涉及外部支付或合规资料则以接口占位与模拟实现完成。每完成一个任务，提交代码、对应接口、迁移 SQL、测试及执行结果，并更新追踪矩阵状态。后端所有接口必须做资源级数据权限校验，前端隐藏按钮不能代替鉴权。
