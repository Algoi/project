# 算法体验与测试操作说明

适用日期：2026-10-17。先打开 [网站](http://192.168.0.128:5173/)，按下面两个例子操作即可。算法已随后端运行，使用时由页面调用。

当前包含两类算法：按历史就餐记录预测未来人数的时序统计算法，以及先按已登记饮食规则过滤、再对菜品评分排序的推荐算法。它们位于独立 `algorithms/` 模块。

## 1. 在网页体验人数预测

1. 使用账号 `canteen`、密码 `canteen` 登录。
2. 顶部网点选择“幸福社区助餐点”。
3. 点击左侧“就餐人数预测”。
4. “供餐日期”选择明天，餐次选择“午餐”，点击“刷新”。
5. 查看“未来七天就餐人数”的曲线和表格。表格列出日期、预测人数、历史样本数；下方展示历史实际人数。
6. 点击“备餐出餐清单”，选择同一日期和餐次，可查看各菜品的已确认份数、预测人数及参考份数。

打开预测页面或点击刷新即可触发计算。未来新订单主要影响已确认份数；人数预测读取过去的实际就餐记录，因此不会每增加一笔未来订单就直接加 1。

判断是否正常：

- 有足够历史记录：显示预测人数和历史样本数。
- 历史记录不足：显示“历史数据不足”。这与真实就餐人数为 0 不同。
- 停餐日：显示“不营业”。
- 演示网点的历史人数很小，显示 1 或 2 人也合理。

当前默认实现是 `weekday_average_v1`：优先取最近历史中相同星期的最多 8 个有效样本，少于 3 个时回退到最近最多 14 个有效样本；有至少 3 个才计算平均人数，四舍五入取整数。例如三个样本为 10、20、30 人，预测为 20 人。

2026-10-17 的实际网页检查中，2026-10-18 至 2026-10-24 每天均预测 2 人、采用 4 个历史样本。自动测试已按每个返回的样本日期读取历史人数，独立复算并核对页面结果。数据变化后结果可以变化。

## 2. 在网页体验菜品推荐

1. 退出食堂账号，使用 `family` / `family` 登录。
2. 点击左侧“为家人订餐”。
3. 在“选择老人”中选择“李阿姨（演示）”。
4. 用餐日期选明天、餐次选午餐。
5. 查看菜品卡片上的“推荐分”和推荐原因。
6. 展开“查看未推荐的菜品及原因”。现有演示档案登记了花生过敏，“花生鸡丁（演示）”应列入排除原因，不能作为可选餐品。
7. 将老人切换为“王大爷（演示）”。现有演示档案未登记花生过敏；在相同已发布菜谱、餐品启用且有剩余份数时，可看到“花生鸡丁（演示）”重新出现在候选中。

这套对照例子使用已有演示档案，不需要修改老人资料。查看推荐不创建订单；点击“提交订单”才进入订餐流程。

如果提示“当天菜谱尚未发布”，需先由食堂账号在“菜谱上报”选择目标日期、餐次并保存、上报，再由社区账号 `community` / `community` 在“每日菜谱维护”选择同一天和餐次确认发布。演示菜谱只初始化一段日期范围，后续日期需要正常维护。

推荐的顺序是：先检查已登记过敏原、禁忌和资料完整性，再对通过检查的候选评分。分数综合营养适配、菜品分类偏好、历史评价和历史选择。分数越高越靠前，同分按固定规则排序。

## 3. 可选：观察推荐权重的影响

1. 先记录相同老人、日期、餐次下的推荐分。
2. 退出并使用 `admin` / `admin` 登录，进入“膳食推荐规则”。
3. 记录原来的四个权重和营养目标，便于恢复。
4. 将营养、偏好、评价、历史选择四个权重依次设为 `0、1、0、0`，点击“保存参数并生效”。这表示只按偏好分项排序。
5. 切回家属账号，重新进入相同老人、日期和餐次的订餐页，比较评分与推荐原因。
6. 体验结束后，用管理员账号恢复原来的参数。

权重必须非负且合计为 1。分项相同的菜品可能仍然同分，顺序不一定发生变化；判断时要同时看分数。调整排序权重不会放开已登记的饮食禁忌。

## 4. 一条命令运行独立算法测试

在项目根目录执行：

```bash
./mvnw -B -ntp -pl algorithms -am test
```

这组测试使用固定输入，不依赖数据库或正在运行的服务。成功时会看到 `Tests run: 5, Failures: 0, Errors: 0` 和 `BUILD SUCCESS`。

| 测试内容 | 固定输入/预期 |
|---|---|
| 同星期均值 | 10、20、30 → 20 |
| 空历史、停餐、真实零 | 分别返回数据不足、停餐标记和 0 |
| 可替换预测实现 | 最近样本 30、20、10，均值为 20；按 3、2、1 加权后四舍五入为 23 |
| 推荐评分与同分顺序 | 分项 80、100、60、50，权重 0.4、0.25、0.2、0.15 → 76.50；同分顺序稳定 |
| 非法输入 | 负人数、权重总和错误、上下限颠倒均拒绝 |

对应代码：[AlgorithmContractTest](../algorithms/src/test/java/com/community/meal/algorithms/AlgorithmContractTest.java)。

## 5. 自动测试网页和数据库联动

整个项目已启动、保留上述演示数据且本机已安装 Chrome 时，可执行网页算法对照测试：

```bash
WEB_BASE_URL=http://192.168.0.128:5173 npm --prefix web run test:e2e -- e2e/algorithms.spec.ts
```

桌面和手机视口各执行人数复算、两位老人推荐对照，共 4 项；会保存截图，并输出实际算法标识、预测样本和推荐排序。查询会按原系统逻辑记录预测结果及推荐曝光。

需要检查数据库与后端算法联动时，执行：

```bash
./scripts/test-server.sh test -Dtest=MenuForecastRecommendationTest,AlgorithmEdgeTest,AlgorithmReplacementIntegrationTest
```

脚本创建独立临时 MySQL 测试库并在结束后清理，验证空历史、样本回退、停餐、推荐过滤、参数校验、替换算法及禁止替换实现返回未获准餐品等行为。运行需要根目录 `.env` 中的本机数据库配置。

现有自动测试验证计算逻辑和业务边界。若要评价真实场景预测准确率，需要另外用真实历史数据回测误差；演示数据不作为准确率结论。

算法切换配置和新增实现方法见 [模块架构](architecture/modularization.md)，本次实际测试与截图见 [验证记录](reviews/algorithm-testing.md)。


## 在网页查看样本和运行历史回测

1. 使用 `canteen/canteen` 登录，进入“就餐人数预测”。预测结果上方显示实际算法标识，每一行“使用的历史日期”对应真实参与样本。
2. 向下找到“历史回测与算法比较”，选择今天以前的起止日期（最多 90 天），点击“运行历史回测”。
3. 比较两个实现的有效比较天数、MAE、RMSE；展开下方“逐日结果与训练样本”核对实际值、预测值与训练日期。每条训练日期必须早于目标日期。
4. 缺失历史人数、样本不足、停餐分别显示；没有有效样本时不显示误差数值。演示数据只用于验证流程，不代表真实业务准确率。

家属订餐页在每道餐品下展开“查看推荐分项”，可以看到营养、老人偏好、历史评价、近期选择的评分与实际配置权重；上方显示算法和配置版本。降级候选没有伪造评分。算法实现仍在独立 algorithms 模块，配置切换后统一重启项目生效。
