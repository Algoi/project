# 完整业务 API v1

基础路径 `/api/v1`，与前端同源部署。除登录外均传 `Authorization: Bearer <token>`。机器可读的完整路径索引见后端静态文件 `/api/v1/openapi.yaml`；下表补充业务字段和边界。第 1 批历史说明保留在 `batch-01.md`。

响应为 `{code,message,data,traceId}`；成功 `code=OK`。参数无效 400、未登录 401、越权 403、不存在 404、唯一性冲突 409、状态/业务规则不允许 422。列表使用 `page=1&size=20`，最多 100；分页响应 `{records,total}`，字典和清单直接返回数组。金额和营养 DECIMAL 返回字符串，日期 `YYYY-MM-DD`，时间戳 UTC ISO 8601。请求不得传客户端计算的订单金额。多个角色的合法资源权限取并集：兼任社区人员的家属仍能按已审核绑定访问自己家人的数据，但不因绑定而获得未授权网点的工作人员权限。

权重非负、总和为 1；营养目标 `targets:{caloriesKcal:{min,max},...}`。推荐先过滤已登记过敏原、疾病禁忌、忌口食材及安全资料不完整的候选，再评分排序；返回原因和推荐事件 ID。默认 `weekday_average_v1` 人数预测采用最近 56 天同星期最多 8 个有效样本，少于 3 个时回退最近最多 14 个有效营业日，仍不足则 `count=null,insufficientData=true`；不编造样本。真实零人数保留、缺失/停餐排除。备餐参考值不低于已确认份数，历史不足 7 天时采用确认份数。预测与推荐响应增加所选实现的 `algorithm` 标识，并随结果/曝光持久化；可用配置选择已注册实现，详见 [模块与算法扩展](../architecture/modularization.md)。推荐安全过滤和下单复核独立于排序算法。

## 订单、支付、退款、交付

### 钱包与独立账单（产品完善第二批）

- `GET /wallet`：FAMILY 本人余额，返回 `balance,updatedAt,canTopup`；初始余额为零。
- `GET /wallet/transactions?page=1&size=20`：本人资金流水、交易后余额、关联订单。
- `POST /wallet/topups`：`{amount,requestId}` 创建充值请求；金额大于零、两位小数以内、最高 10000 元。相同本人请求标识及金额返回原请求，金额改变返回 409；创建不入账。
- `POST /dev/wallet/topups/{id}/confirm`：仅 dev/test 且非 prod，只有本人可确认，模拟到账；重复确认只入账一次。
- `POST /orders/{id}/payments` 支持 `channel=WALLET`：只有家属本人主动选择时扣本人钱包；订单金额由服务端读取，成功直接返回 `SUCCESS`，无需调用模拟支付回调。余额不足返回 422 并回滚。
- 钱包退款在社区审核通过后退给实际付款家属的原钱包；不能因代订者或退款申请者不同而改变收款人。
- `GET /billing?dateFrom=&dateTo=&keyword=&page=1&size=20`：FAMILY 本人实际付款/退款账单，按交易日期、订单号/老人姓名筛选。默认当月，最多一年区间。返回 `records,total,summary:{paidAmount,refundAmount,netExpense}`。充值与未付款订单不算消费。

余额与资金流水同事务、按账户加锁，订单付款和退款防重。只读账单保留既有付款归属兼容；历史模拟支付不转换成余额。生产没有模拟充值确认路由，未配置充值时 `canTopup=false`；余额支付与外部真实收款渠道分开。

创建示例：

```json
{"elderId":1,"siteId":1,"mealDate":"2026-10-18","mealType":"LUNCH","deliveryType":"DINE_IN","items":[{"menuItemId":1,"quantity":1,"recommendationEventId":1}]}
```

`recommendationEventId` 可选。配送另需 `deliveryAddress,contactName,contactPhone`。可传 `Idempotency-Key` 请求头；相同请求重试返回原订单，不同内容拒绝。服务端重算资格、金额及安全约束，按老人和菜品锁定并检查唯一餐次和剩余份数。

待支付占位 15 分钟，过期释放。默认预订今天至未来 7 天，当天必须早于开餐 2 小时；Asia/Shanghai。已备餐不得自行取消。整单退款不超过实付，成功仅一次，补贴账本负向冲减一次。支付和营养均保存订单快照，不随标准菜品或后续资格变化追溯修改。真实资金渠道尚未接入，模拟接口绝不用于生产收款。

## 产品完善新增接口（V10–V11）

所有接口继续使用 `/api/v1`、Bearer 会话和现有响应封装。原有 33 项路由保留。

| 接口 | 数据与权限 |
|---|---|
| GET `/workbench?role=&siteId=` | 当前账号实际持有的单个角色待办；社区/食堂网点须授权，禁止伪造角色 |
| GET `/messages?unread=&keyword=&page=&size=` | 仅本人通知；GET `/messages/unread-count` 返回本人未读数 |
| PATCH `/messages/{id}/read`、POST `/messages/read-all` | 本人已读操作，重复标记不产生额外记录 |
| GET/POST `/addresses`、PUT/DELETE `/addresses/{id}` | FAMILY 本人、当前批准绑定；字段 elderId、label、contactName、contactPhone、address、isDefault；每人每老人仅一个默认地址 |
| GET `/orders` 新增筛选 | keyword（订单号/老人姓名）、elderId、mealType、dateFrom、dateTo；既有 date/status/siteId 保留；详情 events 为实际审计事件时间线 |
| GET `/sites/{id}/delivery-list` 新增筛选 | 可选 deliveryStatus=PENDING/OUT_FOR_DELIVERY/DELIVERED，与原日期/餐次/网点授权合用 |

| POST `/subsidy-applications/{id}/approve` 扩充 | 可选 validFrom（默认今天）、validTo（含当日）；结束不能早于开始；按用餐日确定资格 |

搜索分页导出使用上述原授权读接口分批取出全部匹配数据，只导出页面业务列，不引入可绕过权限的下载接口。消息和进度通过同事务业务事件发布，通知唯一键为接收账号加持久审计事件号，重复业务确认不会重复发送。历史事件无法追溯时页面明确说明，未伪造历史时间线。

多网点补充：GET `/bindings`、`/subsidy-applications`、`/refunds`、`/tickets` 支持可选 siteId，始终与原授权范围取交集。社区待办链接带入所选网点和状态，数量与目标列表一致；未指定 siteId 时保留原有全部授权范围行为。
